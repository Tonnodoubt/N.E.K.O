# UDP 双向打洞方案 v2

## 背景

当前第2层（STUN）连接是单向的：手机往后端发 UDP，后端被动等待回复。
在对称型 NAT 下，后端的回包会被手机的 NAT 丢弃，导致连接失败。

本方案通过引入双向打洞，提升第2层的成功率。

---

## 为什么单向会失败

对称型 NAT 的规则：每次连接不同目标，分配的公网端口都不同，且只允许"已建立连接的对端"的回包进入。

```
手机 NAT 分配：1.2.3.4:50001 → 后端（发出 HELLO）
后端回包到：1.2.3.4:50001
手机 NAT：没有记录允许后端地址进来 → 丢弃
```

双向打洞的原理：双方同时往对方发包，各自的 NAT 都会记录"我主动连过这个地址"，之后对方的包就能进来。

---

## 方案设计

### 总体流程

```
[手机]                    [云注册中心]              [后端]

1. STUN 查公网地址
   ──STUN Request──► STUN服务器
   ◄──公网 IP:Port──

2. 上报公网地址
   ──POST /punch──► 存储 {clientIp, clientPort, TTL=30s}

3.                                               轮询云端
                    ◄──GET /punch────────────────
                    ──{clientIp, clientPort}────►

4. 双方同时互发（打洞）
   ──UDP PUNCH──────────────────────────────────►
   ◄──UDP PUNCH─────────────────────────────────

5. 洞打通，正常握手
   ──UDP HELLO──────────────────────────────────►
   ◄──UDP ACK（含 tcp_endpoint）────────────────

6. 切换 HTTP 业务通信
   ──HTTP/WS────────────────────────────────────►
```

---

## 各端改动说明

### 1. 云注册中心（新增接口）

新增 `/device/punch` 接口，用于手机上报自己的公网地址，供后端读取。

**POST /device/punch**
```json
请求：
{
  "device_id": "xxx",
  "token": "xxx",
  "client_ip": "1.2.3.4",
  "client_port": 50001
}

响应：
{ "ok": true }
```

**GET /device/punch?device_id=xxx&token=xxx**
```json
响应：
{
  "client_ip": "1.2.3.4",
  "client_port": 50001,
  "expires_at": 1234567890
}
```

数据 TTL 设为 30 秒，过期自动清除。不需要持久化，内存存储即可。

---

### 2. RN 端（UdpP2PClient.ts）

在发起第2层连接前，增加以下步骤：

1. 用 STUN 查自己的公网地址（复用后端的 STUN 服务器 47.117.174.64:3478）
2. 把公网地址 POST 到云注册中心
3. 发送 UDP HELLO 的同时，等待后端的 PUNCH 包

关键点：手机端的 STUN 查询必须用**同一个 UDP socket** 来发后续的 HELLO，否则 NAT 会分配不同端口，打洞无效。

```
当前流程：
  创建 socket → 发 HELLO → 等 ACK

改后流程：
  创建 socket → 发 STUN Request（用同一 socket）→ 拿到公网地址
  → 上报云端 → 发 HELLO → 等 ACK（同时接收 PUNCH 包）
```

---

### 3. 后端（udp_server.py + lan_proxy.py）

`UDPP2PServer` 增加主动打洞能力：

1. 启动后开始轮询云端 `/device/punch`（每2秒一次，最多等30秒）
2. 拿到手机公网地址后，主动往手机发 UDP PUNCH 包
3. 继续等待手机的 HELLO，收到后正常回 ACK

`lan_proxy.py` 在启动 UDP 服务器时，传入云端客户端实例，供轮询使用。

## 局限性

即使实现双向打洞，以下情况仍会失败，需要用户自行配置第三方隧道（如 FRP、Tailscale 等）：

- **端口受限型对称 NAT**：要求必须先收到对方的包才开洞，双方同时发也无法解决
- **运营商级 NAT（CGNAT）**：多层 NAT 叠加，打洞成功率极低
- **企业防火墙**：主动拦截 UDP 流量

这是 UDP 打洞的固有限制，业界（包括 WebRTC）也无法完全解决。

---

## 实施顺序

1. 云注册中心：新增 `/device/punch` 接口
2. 后端：`UDPP2PServer` 增加轮询 + 主动 PUNCH 逻辑
3. RN 端：`UdpP2PClient` 改用固定 socket + STUN 查地址 + 上报云端
4. 联调测试：在对称型 NAT 环境下验证成功率
